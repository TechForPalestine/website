✓ S-1 is closed: payment side effects are verified with Qgiv

/api/membership-complete and /api/donation-complete now read only a transactionId from the request and look the transaction up in Qgiv's reporting API (src/utils/qgivVerify.ts). Email, names, tier and marketing opt-in all come from Qgiv's record. The lookup fails closed in every case: missing token, timeout, non-2xx response, mismatched id, status other than Accepted, form not on the endpoint's allowlist, or no email. The tier is chosen by Qgiv formId, so a donation cannot be used to get a membership invite. Confirmed live: a forged Origin with a bogus transaction now gets 402 Could not verify transaction (in v7 the same request reached the business logic). Some weaknesses remain; they are low severity and are recorded as T-3 and T-4.

✓ The response-header and caching findings are closed

Security headers are now set in middleware (src/middleware/security-headers.ts), so SSR responses carry X-Content-Type-Options, Referrer-Policy, Permissions-Policy, X-Frame-Options: DENY and a CSP with frame-ancestors 'none'. The one exception is /newsletter-embed, which allows framing by the site itself. Pages default to private caching, and /admin*, /api/* and non-GET requests get no-store (S-2, S-3). Sentry scrubbing is wired into all three Sentry.init calls (S-5), and the raw-HTML sink in the volunteer form was removed along with the file (S-8).

New findings — detail

T-1
No Strict-Transport-Security header LOW

Files: src/middleware/security-headers.ts · Cloudflare zone settings
OWASP: A05:2021 – Security Misconfiguration

None of the HTML, API or static responses checked carries HSTS. Cloudflare redirects HTTP to HTTPS, but without HSTS a visitor's first plain-HTTP request (from a typed URL or an old link) can be intercepted on a hostile network before that redirect happens. The donate and membership pages make this worth closing.

Fix: Enable HSTS in the Cloudflare dashboard (SSL/TLS → Edge Certificates), or add it to the middleware:

response.headers.set("Strict-Transport-Security", "max-age=31536000; includeSubDomains");

Start without preload, and only add includeSubDomains after confirming every subdomain serves HTTPS.

T-2
Event-description Markdown links are rendered with any URL scheme LOW

Files: src/utils/eventDescription.tsx:69-82 · src/store/eventsClient.ts (resolveLinks) · src/components/events/EventDetailsDialog.tsx:194,205
OWASP: A03:2021 – Injection · Introduced: PR #555 (regression)

#555 replaced the hand-written description parser, which only made links out of https?:// targets, with the marked lexer. The link token's href now goes straight into <a href> without a scheme check. Anyone who can write to the Mattermost Events Calendar can publish [Register](data:…) or a link to an OS protocol handler (ms-officecmd:, search-ms:), and it will appear in the event dialog on /events. javascript: URLs are neutralised twice: React 19 blocks them, and the nonce CSP would block them anyway. That leaves phishing and protocol-handler abuse, and it needs calendar write access, so the severity is Low. The registerLink, locationLink and watchLink fields from the ICS feed were already unsanitised before v7 and should be fixed together with this.

Fix: Reuse the existing helper, as projectsClient.ts already does:

case "link": {
  const href = sanitizeUrl(link.href);
  if (!href) return <Fragment key={key}>{renderInlineTokens(link.tokens, key)}</Fragment>;
  return <a key={key} href={href} target="_blank" rel="noopener noreferrer" className="underline">…</a>;
}

Apply sanitizeUrl to the three link fields in resolveLinks(), and add tests with javascript: and data: links.

T-3
Qgiv verification has no recency or amount check, leaks transaction state, and replay protection fails open LOW

Files: src/utils/qgivVerify.ts:102-155 · src/utils/transactionReplay.ts · src/pages/api/membership-complete.ts:42-65 · src/pages/api/donation-complete.ts:39-66
OWASP: A04:2021 – Insecure Design

S-1's fix is sound: an attacker can no longer cause an invite or subscription for an address that has not paid. These residual gaps all fall short of that:

  • No recency check. Any Accepted transaction on an allowed form, at any age, is acted on once. Qgiv transaction ids are numeric and probably sequential (not confirmed), so ids can be enumerated within the POST rate limit to trigger Hub invites and list tags for real past payers. Those emails go to the people who actually paid, so the harm is unwanted contact and data-integrity noise, not access.
  • Responses reveal transaction state. 402, 200 Not opted in, 200 Already processed and 200 success let an enumerator tell real transactions from fake ones and learn each donor's opt-in choice.
  • The amount is not checked. amount is parsed but never used. If the Pilot Membership form accepts custom amounts, a token payment still earns a paid-tier invite. This depends on the Qgiv form configuration.
  • Replay protection fails open and is not atomic. claimTransaction() allows the request when the KV binding is missing or KV throws (this is deliberate, and documented in the file). Its get then put can be raced by concurrent requests, and keys expire after 30 days, after which the same id can be processed again. The replay keys also share the DROPPED_CONVERSIONS namespace with /api/pipe.

Fix:

  • Reject transactions older than a short window (24–72 h) using Qgiv's transaction date, and keep the replay TTL at least that long. This one change also closes the enumeration and expiry gaps.
  • Return the same response body for every verified outcome, and the same one for every failure.
  • Check amount against a minimum for each form in MEMBERSHIP_FORMS.
  • Move the replay keys to their own KV namespace.
T-4
Fabricated transaction IDs each cost a Qgiv API call and a Sentry event LOW

Files: src/utils/qgivVerify.ts:21,107-126 · membership-complete.ts:41-56 · donation-complete.ts:38-53
OWASP: A04:2021 – Insecure Design / A09:2021

The handlers skip Sentry for invalid-id so that callers cannot burn Sentry quota, but TRANSACTION_ID_PATTERN (/^[A-Za-z0-9_-]{1,64}$/) accepts any made-up id such as "1". Each request with a forged Origin then makes an authenticated call to Qgiv's reporting API with the organisation-wide token, fails as lookup-failed, and is sent to Sentry. A loop can therefore flood Sentry, hiding the real "propagation lag" signal and using up quota. It could also get the Qgiv token throttled, and because verification fails closed, genuine new members would then get no invite. The POST rate limit caps the rate.

Fix: Narrow the pattern to Qgiv's real format (/^\d{1,20}$/). Sample or aggregate lookup-failed reports instead of sending one per request. Consider a per-IP KV counter on these two routes.

Good practices confirmed in the v8 codebase

  • Payment verification is well built. Fixed API base URL, a bounded id pattern, matching of the requested id, a per-endpoint form allowlist, fail-closed on every error path, and the token sent in the POST body rather than the URL. The supporting-member form deliberately gets no Hub invite.
  • No new raw-HTML sinks. The only set:html uses are JSON-LD built from constants. The Hub open-roles descriptionHtml.ts is an allowlisting tokenizer that sanitises hrefs.
  • The newsletter embed's postMessage is checked properly. It checks both event.origin and event.source, and validates and caps the payload.
  • The nav A/B test sets no cookie. It assigns variants with an HMAC of day + IP + User-Agent under a secret resolved through getEnv, and the IP is never stored or sent to the client.
  • The middleware order is pinned by a test (src/middleware/index.test.ts), and the shared withOriginGuard checks Origin before parsing the body, with suffix matching on label boundaries.
  • Test coverage of the security utilities grew substantially. crypto, getEnv, origin, basicAuth, qgivVerify, transactionReplay, safeProxy, sanitizeUrl and validate all have suites now.
  • No secrets in the diff. A pattern scan for keys, tokens, JWTs, DSNs and PEM headers found none.

Method and scope

Static review of the full diff 7c7a563..52e647a (44 commits), with current-file reading of every API route, the middleware chain, the security utilities, the data clients and the components that render upstream content. Each of the 36 findings in the v7 register was re-checked against current code. This was supplemented by pnpm audit against the committed pnpm-lock.yaml and the non-destructive live probes logged above.

Not covered: the ProjectHub, Hub, Qgiv and Mattermost services themselves; Cloudflare dashboard configuration (including the WAF rate-limit thresholds) beyond what live responses reveal; whether the ICS token was rotated after S-5; and authenticated behaviour of /admin/conversions.

Bottom line

The urgent item from v7 is resolved properly. Payment-triggered actions are now decided by Qgiv's own record, fail closed, and the fix was verified against production. The headers, caching and telemetry findings are also closed. What remains is a Medium dependency backlog, mainly the Astro major upgrade and a cheap axios bump, and nine Low items, most of which take under an hour each. The new findings are all small. T-2 is worth noting as a pattern: replacing a hand-written parser with a library silently dropped a scheme check the old code had, and the existing sanitizeUrl helper closes it.
